# Customer Extensions Plan

Goal: this repo ("the cockpit") is where every extension gets developed and browser-verified
against a real tenant. Once an extension is ready for a specific customer, it gets **packaged out**
into that customer's own deliverable — a ZIP and/or a dedicated GitHub repo — without turning this
repo into a pile of permanent per-customer copies.

This is the reverse direction of `docs/PROJECT-ONBOARDING.md` (which governs importing/running
multiple tenants *inside* this one repo via `environments/<tenant>.js` + `settings/<tenant>.js`).
That model still applies for day-to-day multi-tenant development here. Packaging only kicks in
once a customer needs their **own standalone deployment** they can run independently.

## Repo model: one repo per customer

Each customer gets their own GitHub repo, e.g. `github.com/papcont/<customer-slug>-extension`.
Rationale (confirmed): clean separation, lets a customer be given access to only their own repo
if that's ever needed, and each customer's deployment can diverge (their own commit history,
their own release cadence) without affecting this cockpit or any other customer.

## Local layout

```
customer-extensions/
  <customer-slug>.config.json     tracked - what goes into this customer's package
  <customer-slug>/
    manifest.md                   tracked - intake-record-style notes (same shape as the
                                   Extension Intake Process in DEVELOPMENT-ENVIRONMENT-PLAN.md)
    build/                        gitignored - regenerated by the packaging script each run,
                                   never hand-edited
    <customer-slug>-<date>.zip    gitignored - packaging output, not the source of truth
```

`build/` is disposable, like a `dist/` folder — never a permanent parallel copy of the app, in
keeping with "Do not keep complete copied repos as permanent runtime folders" from
`DEVELOPMENT-ENVIRONMENT-PLAN.md`.

### `<customer-slug>.config.json` shape

```json
{
  "customerSlug": "acme",
  "tenant": "acme-prod",
  "targetRepo": "https://github.com/papcont/acme-extension.git",
  "includeCore": ["app.js", "bin", "routes", "views", "public", "settings.js", "package.json", "package-lock.json"],
  "includeModules": ["erp"],
  "excludeModules": [],
  "customFiles": ["public/javascripts/custom/acme-specific.js"]
}
```

- `includeModules` / `excludeModules` map to optional subsystems that aren't every customer's
  concern (e.g. `erp` = `routes/erp.js`, `services/erp*.js`, `views/apps/erp.pug`,
  `public/javascripts/apps/erp.js` and the matching `settings.js` app entry / `servicesEnabled`
  flag). Default is core-only; a customer opts into a module explicitly.
- `customFiles` covers anything genuinely customer-only (per `PROJECT-ONBOARDING.md`'s rule:
  "fork the code only when the customer behavior cannot be expressed as a tenant setting or a
  small custom hook" — this is that escape hatch, kept explicit and small).
- Always included regardless of config: that customer's `environments/<tenant>.js` +
  `settings/<tenant>.js`.
- Never included: `docs/` (internal planning), `tools/` (internal usecase-mining scripts),
  `ERP/` top-level folder (the standalone prototype project, not `services/erp*.js`),
  `graphify-out/`, `docs/tenant-discovery/`, any *other* customer's environment/settings files,
  `.claude/`, `node_modules`, `storage/*`, `.git`.

## Packaging script (not yet built)

`tools/package-customer-extension.js <customer-slug> [--zip] [--push]`

1. Read `customer-extensions/<customer-slug>.config.json`.
2. Copy the resolved file set into `customer-extensions/<customer-slug>/build/` (clean folder
   each run - `createServerFolderPath`-style clear-then-copy).
3. Drop in that customer's `environment.js` (generated from `environments/<tenant>.js` plus the
   secrets currently only in this repo's own gitignored `environment.js` / env vars - **never**
   copy this repo's own `environment.js` wholesale, only the fields that customer's deployment
   actually needs).
4. `--zip`: zip `build/` into `<customer-slug>-<date>.zip` next to it.
5. `--push`: initialize (or reuse) a git working copy in `build/`, commit, and push to
   `targetRepo` - **always shown as a diff/summary and confirmed before the actual push**, same
   rule as any other push to a remote.

Building this script is the next concrete step once this plan is confirmed - intentionally not
started yet, since the exact core file whitelist and the `erp` module boundary should be checked
against a real first customer before being locked in.

## Fusion Manage tenant setup via browser MCPs (sketch only - not implemented)

Once a customer's package exists and their own Fusion Manage tenant is ready, setting it up
(workspace views like `Tree Navigator`, fields, webhooks) often needs the real admin UI, not just
REST calls. This reuses the phased workflow already defined in
`DEVELOPMENT-ENVIRONMENT-PLAN.md` §6:

1. **Discover** - read-only: workspace/field/view inventory via the admin comparison utilities
   already in this app, plus a browser pass (Playwright or claude-in-chrome) over the tenant's
   admin pages to see current state.
2. **Compare** - diff the customer tenant's current state against what the packaged extension
   expects (workspace IDs, field IDs, required BOM views, `servicesEnabled` flags).
3. **Plan** - list the exact objects to create/change (e.g. "create BOM view `Tree Navigator`
   with columns Descriptor/Number/Quantity on workspace 57").
4. **Backup/export** - capture current picklists/views/scripts before touching anything, same as
   `services/erpWebhookRegistrationStore.js`'s pattern of only overwriting when a real diff is
   confirmed.
5. **Apply** - smallest approved change, one object at a time, via browser automation clicking
   through the actual Fusion Manage admin UI where no REST endpoint exists for it.
6. **Verify** - reload the packaged extension against the tenant, browser-check the affected page.
7. **Record** - append to that customer's `manifest.md`: what was changed, when, by what action.

This stays a **per-customer, explicitly-approved** activity - never a bulk/automated rollout
across tenants, and never a write without the tenant, the exact action, and the expected effect
named first (existing hard rule, unchanged).
